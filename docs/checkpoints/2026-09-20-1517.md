## Session summary

React Carburetor (https://github.com/PHPCraftdream/ReactCarburetor) is the user's state engine:
state lives outside the React tree, class components read it through `useCarburetor` and subscribe
to exactly the fields they read, so hooks and an auto-memoizing compiler are both unnecessary. Since
the 11:32 checkpoint the work moved outward from the engine to everything around it, and all of it is
now committed as `73a1431` — 257 files, made after the user explicitly authorised a commit to master.
Push was **not** authorised and has not happened; the remote is still at `72e0cfc`.

Four blocks landed. A lint plugin with 22 rules for the mistakes this engine makes silent, shipped as
`react-carburetor/lint` and working in both hosts (verified by actual runs: one `extends` line in
oxlint, a spread config in ESLint 10). A second, unpublished plugin for this repository's own style,
holding `no-parent-import` with a working autofix. A promise cache, `ResourceCache`, with lifetimes,
deduplication, abort, invalidation, LRU eviction, `useResource`, Suspense and SSR. And an import
alias `@/` replacing every upward relative import, proven not to leak into any of the four published
build variants — JavaScript and declarations alike.

Three defects in the cache came from its own tests, and all three were fixed at the mechanism rather
than papered over: an unescaped key containing the path separator made writing entry `a.b` wake a
component reading entry `a`; eviction dropped the entry it had just created, because that request was
not yet registered; and the LRU order was **flaky** on `Date.now()`, whose millisecond resolution let
"least recently used" stop being defined. The last one is worth remembering — it failed 2 runs in 3,
and the fix was a monotonic counter, now pinned by a test that touches four entries inside one
millisecond.

Dogfooding the lint rules on this repository found four false positives in my own rules, each fixed
in the rule: `preEmit` and its helpers publish already, `suspend()` is built to be called from render,
a non-inline effect body cannot be analysed, and a `map` callback is render code rather than deferred
code. That pattern — the rule is wrong, not the code — is the one to keep.

A native Rust linter was started in `native/` after the user argued that what we ship outward must be
fast and energy-efficient, because at any popularity the rules run in every consumer's CI. Measured
on this tree, 157 files: oxlint's own rules 315 ms, the same plus our 22 as a JavaScript plugin
585 ms, the binary 20 ms including walk, parse and output. The architecture the user chose is that the
JavaScript plugin becomes a **bridge** — it runs the binary once per lint run and reports through the
host — so the rules exist in one implementation and suppressions and editor diagnostics come free.
The hard constraint "exactly once per run" was probed before any Rust was written and it holds:
ESLint default is one spawn for any number of files, oxlint is one, and `--concurrency=4` is one
process with four worker threads sharing `process.pid`, where `SharedArrayBuffer` and `Atomics.wait`
both work — so the losers of the race can wait for the winner's result.

## Decisions

- The lint rules ship as a subpath of the library (`react-carburetor/lint`) rather than a separate
  package, so one version number keeps the rules and the engine semantics in step. A separate package
  was rejected for doubling the release work.
- The plugins are split by what a rule is *about*: carburetor safety ships, house style does not. A
  test asserts the internal rules are absent from the published bundle.
- The native binary is the direction for shipped rules, on the user's energy argument. Internal style
  rules deliberately stay in JavaScript — the user said "мы уж потерпим".
- The JavaScript plugin becomes a bridge to the binary rather than a second implementation, which
  removes the two-implementations maintenance cost and keeps suppressions and editor diagnostics.
- `invalidate` does not refetch, and a failed entry is not retried automatically. Refetching a
  hundred entries because one mutation succeeded is the waste the engine exists to avoid, and
  retrying from render would loop through the re-render the failure causes.

**A real self-caught mistake, worth remembering**: after merging R2-03, I ran
`gh run watch <id> --exit-status | tail -40` in the background and reported "CI green" based on
its reported exit code 0 — but `tail`, not `gh`, is the last command in that pipe, so the exit
code reflects `tail`'s own (always-zero) success, not the actual run's conclusion. The real run
had in fact failed (a `check:layout` violation). Caught by independently cross-checking with
`gh run list`/`gh run view`. Fixed the *habit*, not just that one run: every CI watch from then on
used `gh run watch <id> --exit-status > logfile 2>&1; echo "EXIT:$?" >> logfile` (no pipe), and the
real exit code was read back out of the file afterward rather than trusted from the tool
notification's own summary line.

  to detect.
- **The demo app's own `lib/tsconfig.json` needs to be checked separately from the root
  `tsconfig.json` whenever a fix's typecheck footprint changes** (both this session's own
  `ES2021.WeakRef` miss and the earlier `check:layout` miss came from checking only the most
  obvious verification command and not the demo app's independent build) — added this explicitly
  to every subsequent `/wrush` task prompt's process requirements so later sub-agents wouldn't
  repeat it.

  conclusion when the command was piped** — always redirect to a file and read the real exit code
  back out, or use `gh run view --json conclusion` directly, after any `gh run watch | <filter>`
  construction.

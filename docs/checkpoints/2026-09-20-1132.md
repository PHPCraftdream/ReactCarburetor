## Session summary

React Carburetor (https://github.com/PHPCraftdream/ReactCarburetor) is the user's state engine:
state lives outside the React tree, class components read it through `useCarburetor` and
subscribe to exactly the fields they read, so hooks, dependency arrays and an auto-memoizing
compiler are all unnecessary. This session migrated the 2019-era repository to a modern
toolchain, rebuilt the engine, published the repository, and has now closed the engine review
that followed.

Since the previous checkpoint (10:37) the whole review block finished and shipped as `72e0cfc`,
with CI green on both jobs and 118 passing tests. Seven review findings were implemented with
regression tests: computed composition (a computed reading another computed used to register no
dependency and silently return a stale value), a props/state gate so a parent re-render no longer
cascades into children, `update(mutate)` plus a development warning for a draft write that was
never published, per-effect cleanups with dependency arrays, `CarburetorScope.dehydrate/hydrate`,
a curated public export surface pinned by a test, and an options object for `subscribe`.

Two things in that batch are worth remembering because they were driven by measurement rather
than opinion. First, `pathsIntersect` was benchmarked before deciding anything: matching 500
written paths against 1000 subscribers cost 110 ms (357 ms when nothing matched), which justified
`SubscriberIndex` — read paths and their ancestors are indexed, bringing those cases to 0.47 ms
and a single changed path from 0.39 ms to 0.0009 ms. A differential test pins the index against
the full scan, so the optimization cannot silently change semantics. Second, the development
diagnostics were originally guarded by a runtime `globalThis.process?.env` lookup that no bundler
can substitute — a grep of the production demo bundle proved the warning strings shipped. They
are now guarded by a literal `process.env.NODE_ENV` comparison with the message inside the guard,
verified absent from a production bundle, switchable through `diagnostics.setEnabled(false)`, and
the package additionally ships pre-stripped outputs behind the `production` export condition.

Nothing is in flight. The next ready task is #38: writing into a non-plain value through draft
(`this.draft.someMap.set(...)`) records no path but marks the draft as touched, so `emitUpdate`
concludes "nothing changed" and notifies nobody — a silent lost update. It has not been probed
yet; the probe comes first, then the fix, then regression tests for both that path and the direct
`this.data` mutation path.

After #38 comes a planned lint-rule package (#39–#48): a hazard catalogue for consumer code, then
rules grouped by reads, writes, lifecycle contract, effects, and transactions/SSR/tracking
boundaries, then packaging, dogfooding and docs. The host question is already settled by
research: oxlint supports custom JS plugins (alpha since 2026-03-11) with an API identical to
ESLint's, so one ESLint-compatible plugin serves both oxlint (`jsPlugins`) and ESLint v9 flat
config, and oxlint's `RuleTester` provides the rule tests.

Environment facts that cost time and should not be rediscovered: npm on this machine is pinned by
a global `before = 2026-09-13` config, so dependency versions must be resolved against that
snapshot rather than "latest"; and the library sources live inside `lib/`, which is also the demo
package with its own `node_modules` and therefore a second React copy — hook-based code imported
from `lib/src` gets a null dispatcher unless `react` is pinned in `rstest.config.ts`, which it now
is. Benchmarks live in `benchmarks/` and are deliberately outside the test run.

## Decisions

- The props gate is implemented as `shouldComponentUpdate` with a one-level comparison, which is
  safe here precisely because carburetor-driven updates go through `forceUpdate` and bypass it.
  Accepted consequence: a re-render with identical props is skipped entirely, effects included,
  and a prop rebuilt each parent render counts as changed — the same contract as `React.memo`.
- Diagnostics use a literal `process.env.NODE_ENV` guard with the message inline, rejecting both
  the earlier runtime lookup and the idea of putting the message in its own method — a class
  member survives into a production bundle whatever the branch does.
- The library does not bake `NODE_ENV` into its default outputs; it ships extra pre-stripped
  outputs behind the `production` export condition instead, so consumers keep control. Accepted
  cost: the package grew from 40.1 kB to 78.7 kB and from 82 to 306 files.
- `SubscriberIndex` was added only after the benchmark showed 110 ms on a realistic worst case;
  `pathsIntersect` stays exported as the documented matching semantics and as the reference the
  differential test compares against.
- The lint rules will be one ESLint-compatible plugin rather than an oxlint-native one, because
  oxlint's JS plugin API is ESLint-identical and a single implementation then serves both hosts.

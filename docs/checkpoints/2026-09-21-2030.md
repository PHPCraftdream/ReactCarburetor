**The bridge (#68, done — the big one).** User confirmed the end goal explicitly: the 22 JS rule
files should stop being a second implementation and become bridge calls to the native binary,
since duplicating rule logic in two languages was never the intended end state — only the internal
house-style rules (`max-line-length`, `require-tsdoc`, etc.) stay JavaScript-only. This meant:

- Deleting the hand-written logic in all 22 `plugin/src/Rules/**` files, replacing each with
  `nativeRule(id, description)` — a few lines that read one shared result and report their own
  slice of it.
- `plugin/src/Utils/Native/nativeBridge.mts`: spawns the binary exactly once per lint run. A
  module-scope cache covers the common single-process case; a lock file in the OS temp directory
  plus `Atomics.wait` as a synchronous sleep covers ESLint's `--concurrency` worker-thread case.
  Proved "exactly once" through the real host, keyed by the spawned process's own pid (not a
  before/after file diff, which raced against other test files' own real oxlint spawns).
  Deliberately forces every rule to `error` when invoking the binary regardless of native's own
  defaults, so a rule a consumer turned ON that native has OFF by default still gets computed —
  the host, not native, decides what's actually reported.
- Deleted ~200 RuleTester-based unit tests for the 22 rules, since RuleTester parses source
  in-memory and never touches disk, so it structurally cannot exercise a bridge that shells out to
  read real files — confirmed this by reading oxlint's actual RuleTester bundle before committing
  to the deletion, and got the user's explicit sign-off on losing that test methodology before
  doing it, since deleting ~200 passing tests is exactly the kind of hard-to-reverse action worth a
  check-in first.
- Found and fixed three more real bugs while wiring this up, all confirmed by an actual run before
  believing the fix: (1) `resolveBinary()`'s workspace-fallback path used a fixed number of `..`
  segments, correct for the source location but wrong once bundled into `dist/lint/`'s flatter
  layout — walks upward looking for `native/target/{release,debug}` now instead. (2) ESLint
  crashed on the synthetic report node because it requires `.loc` and never derives one for a node
  its own parser didn't produce (oxlint only needed `.range`) — found by actually running the built
  bundle through both hosts, not by reading either host's docs. (3) `require-bind-for-passed-method`
  false-positived on `this.onPress.bind(this)`, treating `this.onPress` as "passed as a value" even
  though it's the *object* of the `.bind` property access reaching through it, not a bare reference
  — found by dogfooding the finished bridge on this repository's own test suite, which uses exactly
  that pattern on purpose to demonstrate a *different* hazard.
- CI reordered so the native binary builds before `npm run lint`, since linting this repository now
  depends on it existing.

## Decisions

- The JS plugin is a bridge to the native binary, not a second implementation — confirmed
  explicitly by the user after I flagged that this meant deleting ~200 passing RuleTester tests
  with no equivalent replacement at that granularity (native's own 151 unit tests plus the
  conformance/host-integration tests are what covers this ground now instead).
- Internal house-style rules (`max-line-length`, `require-tsdoc`, `no-blank-line-after-tsdoc`,
  `no-parent-import`) stay JavaScript-only, never ported to native — user's own words: "мы уж
  потерпим" (we can live with it).
- `require-tsdoc`'s line-count limit only measures the summary paragraph, never the rationale below
  the first blank line, because this repository's own comment convention is "why, not what" at
  whatever length that needs.
- The native binary always computes every rule at `error` when the bridge calls it, ignoring its
  own configured defaults, because severity is the host's decision — a rule a consumer enabled that
  native has off by default must still be computed or the consumer's choice is silently ignored.
- JS-review findings are being fixed only after independent verification against current code, not
  taken on the review's word — every finding filed as a task so far was confirmed by tracing the
  actual current mechanism, not by trusting the review's own claimed reproduction.

## R24-ENG-01 — resource owned replay writes through a readonly `status` descriptor (P2)

**Contract and path.** `README.md:656-688,826-846,903-911,924-933` documents `setData` admission of supported own enumerable data state, privately owned history of published operations including restricted descriptors, resource wire history and undo/redo through `restore`; there is no resource-only exception for an enumerable readonly data property. A resource can have a valid Idle state with an updated timestamp; the state change below is the timestamp, not descriptor metadata alone. This uses the public `ResourceCarburetor.setData()` and `CarburetorHistory` API, without an unsupported draft definition or raw mutation.

**Bounded actual Bun source repro**, runnable via `bun -e` from this tree (Bun accepts the `.ts` entry):

```js
import {ResourceCarburetor, CarburetorHistory, diagnostics} from
    './lib/src/Carburetor/index.ts';
diagnostics.setEnabled(false);
const resource = new ResourceCarburetor(async () => 'answer');
const history = new CarburetorHistory(resource);
const next = {...resource.getData(), updatedAt: 7};
Object.defineProperty(next, 'status', {
    value: next.status, writable: false, configurable: false, enumerable: true,
});
resource.setData(next);
const before = {
    status: resource.getData().status,
    updatedAt: resource.getData().updatedAt,
    writable: Object.getOwnPropertyDescriptor(resource.getData(), 'status').writable,
};
const undo = history.undo();
let redo;
try { redo = history.redo(); } catch (error) { redo = error.constructor.name; }
console.log({before, undo, redo, status: resource.getData().status,
    updatedAt: resource.getData().updatedAt,
    canUndo: history.canUndo(), canRedo: history.canRedo()});
```

**Actual:** `before:{status:'idle',updatedAt:7,writable:false}`, `undo:true`, `redo:'TypeError'`, current `status:'idle'`, `updatedAt:undefined`, `canUndo:false`, `canRedo:true`. **Expected:** redo returns `true`, reinstalls `updatedAt:7` and the original `writable:false, configurable:false` status flags, then `canUndo:true, canRedo:false`. A second bounded source control with an identically non-writable/non-configurable **`data`** field instead of `status` completed undo/redo, yielding `status:'success', redo:true, canRedo:false`; the failure is the resource-specific status write, not an inability to own arbitrary restrictive fields. A fresh source control with readonly `status:'success'` and changed `data` reproduced the same failed redo.

**Copied runtime confirmation:** a strict Node ES module consumer using CJS `ResourceCarburetor` from `./dist/cjs/Carburetor/index.js` and ESM `CarburetorHistory` from `./dist/esm/Carburetor/index.mjs` repeated the Idle-state scenario: `admitted:true, undo:true, redo:'TypeError', status:'idle', canUndo:false, canRedo:true`. The mixed-format duplicate-copy development warnings appeared on load, as expected; they were not the exception. A separate mixed-format CJS-store/ESM-history ordinary-store control did redo a newly non-writable/non-configurable branch, retained its flags, refused a subsequent strict write, and preserved Map-key identity through an additional native undo.

**Primary source location:** `lib/src/Carburetor/Resource/ResourceCarburetor.ts:184-189` (the unconditional assignment is line 188). Supporting ownership and cursor locations: `lib/src/Carburetor/Tooling/Graph/ownHistoryGraph.ts:51-76`, `lib/src/Carburetor/Tooling/CarburetorHistory.ts:203-217,414-435,450-470`.

**Mechanism, exact source anchors.** `Store/Carburetor.ts:157-183` accepts and publishes `setData(next)`; `Tooling/Graph/ownHistoryGraph.ts:51-76` clones the readonly descriptor and labels it restricted. `Tooling/CarburetorHistory.ts:414-435` captures an owned restricted endpoint, and `:450-470` sends a fresh owned copy to `resource.restore()`. At `Resource/ResourceCarburetor.ts:157-168` replay is recognized and the settled-key/status are computed; then `:177-189` **unconditionally assigns `data.status = status`**, even when both are already Idle, to the exact newly owned replay graph. The assignment throws on its captured non-writable `status` before `super.setData(data)` can publish the endpoint. `Tooling/CarburetorHistory.ts:203-217` restores the retryable cursor after this pre-install exception; the operation remains permanently unredoable with unchanged inputs. For this scenario no Pending normalization was required: this assignment is wholly redundant. **Remedy:** avoid writing an unchanged status during owned replay; when Pending must normalize, produce a fresh owned graph with the normalized field without violating a restricted source descriptor or splitting native aliases, and preserve the endpoint's supported descriptor/cursor semantics. Keep ordinary public restore copying and normalization unchanged.

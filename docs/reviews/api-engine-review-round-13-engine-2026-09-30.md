## Findings

### R13-E01 — P2 — computed delivery transfers an earlier publication to a replacement registration

**Code and mechanism.** Store delivery now takes a registration-generation cutoff before traversing matching subscriber IDs (`lib/src/Carburetor/Store/Carburetor.ts:404-411`), but `Computed.deliver()` takes only an ID snapshot and looks up the **current** callback under each captured ID (`lib/src/Carburetor/Derived/Computed.ts:526-543`). `Computed.subscribe()` replaces a callback with the same public ID in its `Map` (`Computed.ts:153-159`). If an earlier listener replaces a later listener while a changed computed value is being delivered, the new listener is called for a publication selected before it existed. This is the analogous *computed* edge of the store-only R12-E03 repair, not a renewed claim about store `notifyWrites`.

**Executed probe:** imported `Carburetor` and `computed` from `./lib/src/Carburetor/index.ts`, started `{n:0}`, created `computed(r => r(store).n)`, registered `first` before `target`; `first` calls `computed.subscribe(() => calls.push('replacement'), {id:'target'})`, and the original `target` pushes `old`. `store.setData({n:1})` printed `{"calls":["first","replacement"],"version":1}`. Expected for this first publication: `['first']` (old target cancelled/replaced; new target starts at the next publication). `Core.test.tsx:334-399` covers unsubscribe, a new different ID, and replacing a leaver with a **different** ID, but not replacement of an already-captured ID. A computed subscriber can be an effect or externally mounted view; this produces a real extra invocation, not merely an implementation detail. Acceptance: skip stale same-ID replacement during one delivery while allowing a genuinely later/nested publication to notify the new registration; keep unsubscribe, joiner and exception isolation behavior.

### R13-E02 — P2 — prototype-only replacement is invisible to tracking, history, and restore

**Code and mechanism.** Both `diffPaths.walk` and `applyDiff.applyKey` recurse into trackable values when `sameKind()` approves them (`lib/src/Carburetor/Store/Paths/Diff/diffPaths.ts:90-119`; `applyDiff.ts:39-59`). `sameKind` checks *only* `Array.isArray(a) === Array.isArray(b)` (`sameKind.ts:1-11`). Ordinary `{}` and supported `Object.create(null)` are therefore deemed the same kind even when their own keys/values are identical and their inherited behavior differs. Diffing records no write; `setData` adopts the new object but leaves version, subscriptions, computed native epoch, and history untouched (`Carburetor.ts:162-185,559-596`). `restore` instead only applies own-key differences to the *existing* object, so the requested null prototype never lands (`Carburetor.ts:208-231`). This is not R12-E02's inherited-name becoming an own property: here the **prototype of an entire otherwise-identical container changes**. The README explicitly supports null-prototype dictionary copying, and `sameSelection.ts:84-86` already treats the prototype as visible selection content.

**Executed probes:** with `const s = new Carburetor({item:{}})`, a `watch(d => typeof d.item.toString, onChange)` and `s.setData({item:Object.create(null)})` produced `{"raw":true,"tracked":"undefined","version":0,"wake":[]}` (`raw` checks that the new `item` really has null prototype). A subscribed `computed(r => typeof r(s).item.toString)` instead remained `'function'` after the write, while raw `typeof s.getData().item.toString` was `'undefined'`; `getVersion()` remained `0`, subscriber count of changes remained `0`, and `CarburetorHistory.canUndo()` remained `false`. Separately, `new Carburetor({item:{}}).restore({item:Object.create(null)})` produced `{"restored":false}` for `Object.getPrototypeOf(getData().item) === null`. Expected: the read/prototype change is published to the affected branch (and reversible in history); restoring a snapshot installs its null-prototype shape. Cover both directions, root and nested dictionaries, equal own keys and mixed leaf changes, `watch`/computed, history, and a same-prototype control. Do not defeat the unrelated-leaf precision optimization for ordinary replacements.

### R13-E03 — P2 — selected Map keys are copied once through a read proxy and again through raw Map traversal

**Code and mechanism.** A tracked plain-object branch read returns a proxy (`lib/src/Carburetor/Store/Tracking/createReadProxy.ts:256-275`); an opaque Map branch is returned raw (`:277-279`). `detachOpaque` uses a `WeakMap` keyed by the **input object's identity** when copying plain objects, Maps and Date (`lib/src/Carburetor/Store/Utils/Selection/detachOpaque.ts:42-87,99-139`). A selection `{key: view.key, index: view.index}` can thus contain a read proxy for a plain object and a raw Map that holds that very object's raw identity as a key. The graph copier sees two different identities (proxy and raw target), makes two plain-object copies, and loses `copy.index.get(copy.key)`. `watch` routes selected objects through this helper (`Carburetor.ts:363-383`; `detachWatchSelection.ts:7-19`); `useCarburetorValue` also uses it (`lib/src/Interop/useCarburetorValue.ts:86-98,229-245`). Unlike R11-05, the key here is a **plain trackable object**, not a Date; its proxy/raw duality is what defeats `seen` even after the Date fix. The consumer uses a key from the *detached graph*, not the original key: the documented miss for lookup with an original key does not apply.

**Executed public-consumer probe:** subclass `Carburetor` with `change() { this.update(d => { d.index.set('extra', 2); }); }`; initialize `const key={id:1}; const store=new Store({key,index:new Map([[key,'answer']])})`; call `store.watch(d => ({key:d.key,index:d.index}), next => observed.push({lookup:next.index.get(next.key),same:next.index.keys().next().value===next.key}))`, then `store.change()`. Actual output `{"raw":"answer","observed":[{"same":false}]}`: JSON omits `lookup` because it is `undefined`; expected `lookup:'answer', same:true`. Both occurrences belong to one source object. A separate Date-key control passed (`dateAliased:true,dateLookup:'ok'`). Acceptance: retain identity/lookup topology across the tracked-proxy/raw-Map boundary for both property traversal orders, Set membership and `watch`/hook selectors; keep read tracking, detached mutation isolation and the existing live-class-instance policy.

- The latest nested throttle behavior was exercised from current TypeScript source, not a built artifact: recursively flush `inner` while outer `first,later,end` are captured, cancel/replace `later` in `inner`; observed `['first','inner','replacement','end']` (no obsolete callback). A recursive requeue with `maxUpdateDepth=4` invoked four callbacks, threw the depth guard, and accepted a subsequent clean callback. - No meaningful new speed or allocated-byte regression is established. Operation/allocation evidence: registration mints one globally unique internal key **only for a new local ID**, reuses it for replacement (`Carburetor.ts:279-289`); throttle traversal uses `Map.forEach` instead of materializing callback arrays and reuses a cleared map (`ComponentUpdateThrottle.ts:135-146`); failure arrays are lazy in the store, computed delivery and throttle. These observations are not timing, memory, or throughput measurements, and the three correctness findings are not speculative performance claims.

## R15-ENGINE-01 — Nested notifications misattribute patches to history entries (P2)

**Affected paths.** `lib/src/Carburetor/Tooling/CarburetorHistory.ts:53-56,76-89,148-203` collects patches in one unscoped `pendingPatches`/`pendingOpaque`, then on each wildcard subscription callback builds an entry and unconditionally clears that shared pending collection. `lib/src/Carburetor/Store/Carburetor.ts:394-429` delivers matching subscribers synchronously by registration order and supports a callback starting another `notifyWrites` before the outer callback pass finishes. The write proxy reports the patches at mutation time (`Store/Tracking/createWriteProxy.ts:405-432`), not at history's later subscription turn. There is no publication identity associated with the pending patches.

**Deterministic actual-source consumer reproduction** (`bun -e`, importing this worktree's `lib/src`, no test suite): subclass a public `Carburetor({x:0})` with `set(v) { this.update(d => { d.x=v; }); }`. Register a **one-shot** store subscriber that calls `set(2)` on the first `x===1`; *then* construct `new CarburetorHistory(store)`; call `set(1)` and undo twice. The observed values are:

```json
{"order":"observer-first","after":2,"nested":1,"first":2,"second":0}
```

Both `undo()` calls returned `true` in the initial repro, yet the first left `x` at `2`. The nested `set(2)` reaches history before the outer `set(1)` does; the inner recorder absorbs both patches into one entry (its baseline advances to `2`), and the outer recorder creates a second entry without patches, with `before` and `after` both `2`. A registration-order control using the same one-shot observer but constructing history **before** subscribing produced `{"order":"history-first","after":2,"nested":1,"first":1,"second":0}`. This isolates an order-dependent loss of undo granularity, not a subscriber firing again during undo. A plain transaction intentionally coalesces changes, whereas these are two separately published synchronous operations; this scenario has no open transaction or throttle.

**Required behavior.** Attribute patches/opaque fallback to their actual publication across nested delivery and never claim a successful history step for a no-op introduced solely by reentrant delivery. In both subscriber orders, independently undoing the second operation must restore `x=1`, and undoing the first must restore `x=0`; preserve the existing intentional transaction/throttle coalescing semantics and isolated callback delivery.

## R15-ENGINE-02 — Subscriber writes during undo are mistaken for replay writes (P2)

**Affected paths.** `lib/src/Carburetor/Tooling/CarburetorHistory.ts:109-135` moves an entry between the past and future stacks before applying it. `:148-166` suppresses **every** patch and record while `applying` is true, regardless of whether it originated in replay or in another store subscriber. `:217-231` calls public `carburetor.restore(state)`, which publishes synchronously (`Store/Carburetor.ts:208-232,394-429`); unrelated subscribers can legally write in that notification. Afterwards history sets `baseline` to the planned `state`, not the actual final store state, and leaves `future` intact.

**Deterministic actual-source public-consumer reproduction** (`bun -e`, same frozen TypeScript): create a subclass exposing `patch(f) { this.update(f); }`, a store `{x:0,y:0}` and its history. Patch `x` to `1`. Register a subscriber that, on the undo notification showing `x===0 && y===0`, publishes `y=1` once. Call `undo()` and then `redo()`:

```json
{"undo":true,"afterUndo":{"x":0,"y":1},"nestedWrites":1,"redoable":true,"redo":true,"afterRedo":{"x":1,"y":0},"undoable":true}
```

The subscriber's `y=1` is a real separate public action, not an attempted mutation of a read proxy. It was visible after undo, but redo discarded it without any explicit consumer write to `y`. Its patch and notification arrived while `applying` was true, so history dropped both, retained a future entry that should not silently overwrite this new branch, and advanced its baseline to `{x:0,y:0}` despite actual `{x:0,y:1}`. This defect also occurs if the earlier nested-delivery recorder bug is repaired: no pre-existing subscriber participates in the forward `x=1` update here.

**Required behavior.** Distinguish replay-owned writes from independent writes caused by replay's published event; retain the latter as real changes, reconcile history's baseline to actual state, and handle redo-branch invalidation consistently with an ordinary new write. Exercise both patch and opaque/snapshot replay, and a subscriber that writes a different field so an accidental restore of the intended replay target cannot hide data loss.

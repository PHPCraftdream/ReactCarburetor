## R14-E01 — supported array prototype is changed or rejected by selection detachment

**Contract and mechanism.** An array whose prototype is `Object.prototype` is within the engine's trackable container boundary (`lib/src/Carburetor/Store/Tracking/isTrackable.ts:2-10`). The R13 supplemental prototype acceptance includes such arrays: `sameKind` distinguishes their prototypes (`Store/Paths/Diff/sameKind.ts:11-15`) and `deepClone` preserves them (`Store/Utils/deepClone.ts:19-27`). But the shared selector graph copier creates `[]` for every trackable array except one whose prototype is `null` (`Store/Utils/Selection/detachOpaque.ts:120-149`). Thus an `Object.prototype` array is copied as an `Array.prototype` array. Moreover, its optional class-selection guard rejects any prototype other than `Array.prototype` or `null` (`:123-125`), incorrectly classifying the accepted `Object.prototype` array as an Array *subclass* (`Component/Connection/detachSelection.ts:8-17,29-30`). `sameSelection` compares array prototypes (`Component/Connection/sameSelection.ts:135-150`), so every subsequent matching write can look unequal even when the selected contents did not change. This is a selection-only gap in the prototype cutover, not the earlier R13-E02/E02A diff, clone, or history failure.

**Executed public `watch` probe:** construct `rows = Object.setPrototypeOf([1], Object.prototype)`, `new Carburetor({rows,other:0})`, and watch `d => ({rows:d.rows,positive:d.other>0})`. Public `setData({rows,other:1})` followed by `setData({rows,other:2})` printed:

```json
{"seen":[{"nextPositive":true,"priorPositive":false,"nextProto":false},{"nextPositive":true,"priorPositive":true,"nextProto":false}],"version":2,"rawProto":true}
```

The second `onChange` is wrong: `positive` stayed `true`, the `rows` object and contents stayed fixed, and only the unselected numeric `other` changed. Both delivered snapshots report a false `Object.prototype` check despite the raw array retaining that prototype. An additional bounded source probe showed `s.snapshot().rows` **does** retain `Object.prototype`, so the discrepancy is detachment, not store cloning. Feeding `s.read(...).rows` to the actual class selection detacher printed `{"message":"detachSelection() cannot snapshot an Array subclass (Object): copying it would forge an \"instanceof Object\" object whose constructor never ran and whose private fields were never installed. Select a plain array (for example Array.from(value)) or project the fields the child needs instead.","rawIsArray":true,"rawProto":true}`. The class bridge calls this detacher from `Component/AntiHookComponent/Reads.tsx:177-180`.

**Acceptance:** preserve every supported array prototype in detached watch/hook snapshots, keep the class-selection rejection for actual `Array` subclasses with private state, and admit supported ordinary/null/`Object.prototype` arrays without forging an instance. Check prototype and sparse-index topology, read-proxy/raw-key aliasing, `watch` changes when only a comparator input moves to the same selected result, and a class connection selecting such an array. Do not broaden the state model to unrelated array prototypes.

## R14-E02 — ordinary built-ins lose selected own data fields

**Contract and mechanism.** The README explicitly says selected plain objects, arrays, Map, Set, and Date values are detached, and then says own data fields (including non-enumerable ones) survive and accessor fields are rejected (`README.md:670-678`). `detachOpaque` walks `Reflect.ownKeys` and preserves descriptors for copied objects and arrays (`Store/Utils/Selection/detachOpaque.ts:120-173`), but its ordinary `Date`, `Map` and `Set` branches (`:77-109`) return immediately after copying native time/entries/members; none copies or even inspects the built-in instance's own properties. This is not a request to clone arbitrary class instances: those intentionally remain live or are rejected. These values have the exact native prototypes required by the existing copier, and their own descriptors are visible on the selected source.

**Executed actual-source probes:** a native `Map([['id',1]])` with an own non-enumerable writable `label:'current'` was selected by the public `watch(d => d.index, callback)`; a subclass wrote via `this.update(d => { d.index.set('id', 2); })`, so the watch fired normally. It printed `{"rawLabel":"current","seen":[{"value":2,"own":false}]}`: native Map data was copied, but the selected Map no longer had the own `label`. A separate three-type `detachOpaque` control placed the same hidden `label` and an own symbol-tagged data property on exact-prototype `Map`, `Set` and `Date`: all three returned copies of their corresponding built-in types, all three had `Reflect.ownKeys(copy) === []`, and all three lacked both descriptors. The documented accessor rejection is likewise bypassed for these own fields rather than invoking the getter or reporting the boundary. Watch, class selection and hook snapshots all route through this copier (`Store/Utils/Selection/detachWatchSelection.ts:7-19`, `Component/Connection/detachSelection.ts:29-30`, `Interop/useCarburetorValue.ts:90-96`).

**Acceptance:** for ordinary Map/Set/Date, preserve own string and symbol data descriptors (including flags), recursively detach their values through the *same* graph memo so cycles and cross-links survive, and reject own accessor descriptors without running getters. Continue copying native contents and retaining the documented custom-instance boundary; selecting only native contents should remain unchanged.

## R14-E03 — real Array subclasses bypass the class-selection boundary

**Parent-observed failure; causal source reviewed, not rerun.** The integration owner reported its full-suite run returned **1245/1247**, with the two failures in `__tests__/Engine/Component/AntiHookComponent/selection/array-subclass-boundary.test.tsx:74,108`: both mounted class selections expected an actionable `Array subclass` error in an error boundary, but the boundary message was `undefined`. Those existing tests select a real subclass with a `#private` field directly and nested inside a plain envelope (`:3-17,45-115`); this is the supported pre-existing R12-01 refusal contract, not a newly proposed limitation. Per the stated review constraints and the rule against rerunning reported failures, this reviewer did **not** rerun the parent's test command.

**Mechanism.** `isTrackable` rejects a genuine `Array` subclass because its prototype is not `Array.prototype`, `Object.prototype` or `null` (`lib/src/Carburetor/Store/Tracking/isTrackable.ts:2-10`). In `Store/Utils/Selection/detachOpaque.ts:111-118`, the generic `!isTrackable(value)` branch first hands that subclass back **live**. The intended `onArraySubclass` rejection in the later array branch (`:120-125`) is therefore unreachable for a real subclass; `Component/Connection/detachSelection.ts:8-17,29-30` supplies precisely this guard, but never receives the call. This is distinct from E01's opposite behavior on an **accepted** `Object.prototype` array: both stem from ordering/prototype classification in the same copier, yet one wrongly rejects supported arrays while the other fails to reject unsafe subclass instances. A live Array subclass returned to a gated child is not the promised detached snapshot; it can carry mutable data and private-state behavior across render attempts without the selected graph being copied.

**Acceptance:** the two existing mounted boundary cases must again surface the actionable subclass error, before any child can receive a live Array subclass, while plain arrays and supported `null`/`Object.prototype` arrays detach without a false subclass error. Preserve the established opaque custom-instance policy and avoid pretending to reconstruct an Array subclass by swapping its prototype onto `[]`.

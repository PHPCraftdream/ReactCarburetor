## Находки

### R12-E01 — P1 — локальный ID разных stores сталкивается в общем throttle

**Код и договор.** `Carburetor.subscribe` принимает вызываемый произвольный `options.id`, хранит его в *своём* `subscribers` и индексе (`lib/src/Carburetor/Store/Carburetor.ts:268-289`; контракт `lib/src/Carburetor/Models/Store.ts:25-30`). Каждый store передаёт этот локальный ID непосредственно в общий ему `IUpdateScheduler` при `notifyWrites()` (`Carburetor.ts:405-412`), при отмене и замене (`:281-284,311-317`). У `ComponentUpdateThrottle` одна `Map<string,TUpdater>` на экземпляр планировщика: `schedule(uid, updater)` перезаписывает прежнее значение (`lib/src/Carburetor/Store/Scheduling/ComponentUpdateThrottle.ts:14-25,43-53`), а flush обходит лишь оставшиеся значения (`:87-113`). Конструктор store принимает переданный объект планировщика без требования единоличного владения (`Carburetor.ts:80-90`); `options.id` документирован как ID подписки внутри store, не как глобальный токен всех stores.

**Минимальный сценарий [INFERENCE].** Создать `const scheduler = new ComponentUpdateThrottle(40)` и два `new Carburetor({n: 0}, scheduler)`. Подписать в каждом свой callback с `{id: 'view'}`. Выполнить `a.setData({n: 1}); b.setData({n: 1})` до срабатывания таймера: в карте остаётся только callback `b`; `a` не получает обновления и его UI/наблюдатель остаётся со старым значением до следующего подходящего события. Если между двумя публикациями вызвать `a.unsubscribe('view')`, его `cancel` удалит уже запланированный callback `b` — не придёт ни один. Это затрагивает именно совместно используемый планировщик и публичные локальные ID; автоматически созданные `getUid()` ID глобально уникальны, поэтому сценарий с ID по умолчанию не обнаружит ошибку. R11-06 исправил отмену *внутри* текущего flush для одного ID, но не дал ему пространство имён store.

**Исправление/приёмка.** Давать scheduler внутренний ключ, уникальный для `(store, локальный ID)`, неизменяемый между `schedule` и `cancel` одной регистрации; не менять возвращаемый пользователю локальный ID и семантику замены в одном store. Проверить два store с одним ID и общим scheduler, обе перестановки публикаций, отмену только одного, замену callback во время flush, независимые подписки с автоматически сгенерированными ID, а также исключения/реентрантность. Не заявлять ускорения: реальная потеря доставки вытекает из перезаписи карты, но runtime-проверка этого среза не была выполнена.

### R12-E02 — P2 — унаследованный `toString` не просыпается, когда становится собственным полем

**Код и договор.** `createReadProxy` объявляет любое найденное только в prototype свойство нерегистрируемым и при `get` сразу возвращает унаследованное значение без записи пути (`lib/src/Carburetor/Store/Tracking/createReadProxy.ts:11-20,235-250`). Это разумно для `array.map` как метода, но обычное plain-object состояние вправе иметь собственное перечислимое поле `toString` или `constructor`: draft `set` создаёт/записывает такое поле и объявляет его путь (`lib/src/Carburetor/Store/Tracking/createWriteProxy.ts:350-426`), а `SubscriberIndex` сообщает только записанные read paths (`lib/src/Carburetor/Store/Paths/SubscriberIndex.ts:168-193`). При отсутствии захваченного пути также не помогает новая проверка `Computed.hasDrifted`: `leafVersionsDrifted` обращается к `hasDriftSince(version, emptyReads)`, который возвращает `false` при записи этого ключа (`lib/src/Carburetor/Derived/Freshness/leafVersionsDrifted.ts:19-29`; `lib/src/Carburetor/Store/Paths/WriteLog.ts:87-114`). Указанные собственные строковые свойства соответствуют модели состояния: R6 исключил символы и accessors, не собственные ключи `Object.prototype`.

**Минимальный сценарий [INFERENCE].** У пустого `{}` вычисление `computed(read => typeof read(store).toString)` даёт `'function'`. Затем `store.update(draft => { (draft as Record<string,unknown>).toString = 7; })` — через публичный метод подкласса, так как `update` защищён. `store.getData().toString` теперь `7`, но никакая зависимость вычисления не подписалась на ключ; `computed.get()` по сохранённой версии и пустому read set продолжает возвращать `'function'`, наблюдатели не извещаются. Аналогично сырой `watch(data => data.constructor, ...)` пропускает появление собственного поля. Прямой читатель *уже существующего собственного* поля и чтение отсутствующего также работают; пробел именно в переходе «унаследованное → собственное». Прежнее R14-08 исправляло лишние подписки от методов, а не эту смену значения допустимого ключа; это не повтор ранее закрытой находки.

**Исправление/приёмка.** Различать вызываемые унаследованные прототипные методы на массивах, которые не могут стать валидными индексами состояния, и потенциально затеняемые поля обычного объекта; для последних фиксировать путь чтения или эквивалентный маркер появления own-key, не возвращая wildcard для каждого `map`/`filter`. Проверить `toString`/`constructor`/`__proto__` как собственные данные, `get` до и после добавления/удаления, `watch`, прямой computed и его цепь, независимую запись, а также отсутствие лишних уведомлений от чтения обычных array methods. Риск — *пропущенное обновление*, не измеренная производительность.

### R12-E03 — P2 — синхронный обход вызывает callback другой регистрации под тем же ID

**Код и договор.** `notifyWrites()` заранее вычисляет `this.subscriberIndex.match(writes)` — набор *ID*, не снимок регистраций (`lib/src/Carburetor/Store/Carburetor.ts:392-412`); перед каждым вызовом берёт **текущий** `this.subscribers[id]`. `subscribe()` может заменить запись и read set с тем же ID во время обхода (`:268-289`). По умолчанию `SyncUpdateScheduler.schedule` немедленно исполняет callback (`lib/src/Carburetor/Store/Scheduling/SyncUpdateScheduler.ts:9-23`). Поэтому прежняя причина, по которой ID попал в match, может уже не относиться к новой регистрации.

**Минимальный сценарий [INFERENCE].** Store `{n:0, other:0}`, подписчики `a`, затем `b` (первоначально оба wildcard). При записи только `n` callback `a` делает `store.unsubscribe('b'); store.subscribe(newB, {id:'b', reads: пути, полученные от чтения только other})`. В сохранённом наборе match ещё есть `'b'`; обход достаёт `newB` и вызывает его для записи `n`, хотя новая подписка на `other` появилась *после* этой записи и не должна на неё срабатывать. Если callback новой регистрации запускает запись, эффект или дорогую выборку, это ложная доставка/реентрантность; повторная замена может вызвать некорректные побочные действия. При throttled flush R11-06 отдельно отменяет старую ожидающую запись, а новая store-регистрация без новой записи не ставит новую в очередь (`__tests__/Engine/Store/ComponentUpdateThrottleDelivery.test.tsx:121-139`); немедленный и отложенный режимы сейчас расходятся.

**Исправление/приёмка.** Отменять доставку ID, если регистрация, благодаря которой он оказался в данном match, снята/заменена; вновь подписанную регистрацию запускать только для нового совпавшего события. Проверить unsubscribe и same-ID replace из первого callback, смену read set на непересекающийся, вложенную публикацию, сохранение порядка и исключения, оба вида планировщика. Нельзя просто оставить старый захваченный callback: после unsubscribe он тоже не должен вызываться. Не требуется копировать все callback на каждой доставке, если поколение регистрации можно проверять экономнее.

## Закрытие релевантных R11 и границы

- **R11-02 — закрыт в просмотренной логике, без runtime-сертификации.** `Computed.isStale()` всегда проверяет leaf drift (`Computed.ts:202-221`); native-only совпавшая глобальная эпоха позволяет O(1) ответ, но `Carburetor.emitUpdate` увеличивает её до отложенного `UpdateBatch.add` и до throttle (`Carburetor.ts:559-597`). При расхождении эпохи `leafVersionsDrifted` проверяет версии/записанные пути, а явный `get()` не переносит `announced`, поэтому позже доставленный callback всё ещё сравнивается с прежней публикацией (`Computed.ts:384-390,414-439,494-515`). Цепь/ромб, прямые + производные зависимости и ошибочный body охвачены новым `DeferredFreshness.test.tsx:182-291`. `captureLeafVersions` размечает все листья как native только при проверенном `getVersion` **и** `emitUpdate`; версия адаптера с переопределённым методом остаётся на медленном пути (`Freshness/captureLeafVersions.ts:26-55`, `Scheduling/isNativeStoreSource.ts:8-13`). Доказательств некорректной классификации при соблюдении контракта store не найдено; latency/allocations не измерялись.
- **R11-03 — указанная ошибка новых object/index ключей закрыта, без runtime-сертификации.** `isOpaqueDescriptor` применяет native defaults `?? existing?.flag`, отвергая опущенные `writable/configurable/enumerable` для нового поля; `set` и `deleteProperty` регистрируют путь/патч только после успешного `Reflect.*` (`createWriteProxy.ts:42-47,350-429,439-507,520-549`). Тесты в `DefinitionHistory.test.ts` охватывают отклонённые дескрипторы, версии и историю. Специальное native-array `length` с `writable:false` сохранено осознанно и прямо тестируется (`WriteProxyArrayPrecision.test.ts:390-411`): не считать его ранее исправленным обычным data-key и не выдавать намеренную совместимость за новую R11-03 регрессию.
- **R11-06 — закрыта описанная отмена уже захваченного callback, без runtime-сертификации.** Flush сохраняет mutable `flushing`, `cancel()` удаляет ещё не исполненный ID из неё, а `schedule` заменяет захваченный ID, откладывая новый callback на следующую итерацию (`ComponentUpdateThrottle.ts:43-53,87-113`). Проверки отмены, same-ID замены, публичной отписки, React-unmount и защиты от циклов находятся в `ComponentUpdateThrottleDelivery.test.tsx:17-199`. R12-E01 — иная, *межхранилищная* коллизия локальных ID; R12-E03 — иная, синхронная доставка по прежнему ID.
- **Граф detached selection:** `detachOpaque` теперь заносит копию `Date` в общую `seen` до возвращения, как уже делал для Map/Set/plain container (`Store/Utils/Selection/detachOpaque.ts:51-88,99-140`); соответствующие consumer-тесты `DateAliasConsumers.test.tsx` осмотрены. Зависимости через live class instances оставлены намеренно непрозрачными; доказанной новой ошибки допустимого графа не найдено.

Повтор старых предложений о стоимости обходов `diffPaths`/proxy tree не добавлен в находки: ни нового контрпримера корректности, ни парных измерений для повышения приоритета этого уже описанного направления нет.

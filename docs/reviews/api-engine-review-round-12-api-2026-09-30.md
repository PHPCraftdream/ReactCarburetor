## R12-API-01 — P2 — Undo/redo однослотового ресурса теряет ключ ответа

**Механизм.** `ResourceCarburetor.snapshot()` добавляет `key: settledKey`, отсутствующий в `getData()` (`lib/src/Carburetor/Resource/ResourceCarburetor.ts:43-47,72-83`). Обычные смены статуса/данных ресурса записываются через draft (`:295-310,370-385`), поэтому `CarburetorHistory` получает *патчи полей состояния*, а не полный snapshot (`lib/src/Carburetor/Tooling/CarburetorHistory.ts:148-160,187-204`). Его зеркальный `baseline` создан по `snapshot()`, но применение патчей никогда не обновляет `baseline.key`; `redo()` реконструирует состояние именно из этого зеркала и отдаёт его `restore()` (`:217-248`). Последний устанавливает `settledKey` из переданного `key`; `suspend(args)` считает Success пригодным только для совпавшего ключа (`ResourceCarburetor.ts:108-114,164-183`). Это отдельный потребитель snapshot-контракта, который исправление persistence R11-04 не охватывает.

**Реальный smoke.** `const r = new ResourceCarburetor(async () => 'same'); const h = new CarburetorHistory(r); await r.load('a'); h.undo(); h.redo();` — вывод `r.snapshot()` после redo: `{"status":"success","data":"same","updatedAt":1790726132140}` (**без** `key`), а `r.suspend('a')` бросил новый Promise вместо возвращения `'same'`. В другом окружении значение времени будет иным; отсутствие ключа определяет результат. Нормализация исторического Pending в Idle при undo сама по себе ожидаема; проблема — именно потеря идентичности при повторной установке Success.

**Исправление/приёмка.** Для ресурса каждый сохраняемый history-entry должен хранить и восстанавливать ключ наряду с данными (например, snapshot-entry для изменения приватной wire-идентичности либо поддерживаемый patch seam), не притворяясь, что патчи только по `IResourceData` достаточны. Проверить `load('a') → undo → redo → suspend('a')` (нет нового loader call), `suspend('b')` (есть запрос), Error по своему ключу, затем новую запись и повторное undo/redo; отдельно cache-history и обычные патчи без регрессии.

## R12-API-02 — P2 — Restore может изменить аргумент ответа без публикации

**Механизм.** `ResourceCarburetor.restore()` сначала переназначает `settledKey`, затем вызывает `setData` с четырьмя обычными полями без ключа (`lib/src/Carburetor/Resource/ResourceCarburetor.ts:108-137`). `Carburetor.setData()` объявляет изменения только по `diffPaths(previous, data)`, а `emitUpdate()` возвращается без повышения версии/уведомления при пустом diff (`lib/src/Carburetor/Store/Carburetor.ts:158-181,559-589`). Поэтому две корректные snapshot-записи с одинаковыми `{status,data,error,updatedAt}`, но разными `key`, меняют результат `suspend(args)` без какого-либо `getVersion`/subscribe-события. Синхронный `persist` пишет только по подписке (`lib/src/Carburetor/Tooling/persist.ts:35-51`); DevTools также ждёт публикации и кэширует `toJSON()` по версии (`lib/src/Carburetor/Tooling/connectDevTools.ts:35-50,63-69`). Оба продолжают отдавать прежний ключ.

**Реальные smoke-пробы.** При фиксированном `Date.now = () => 100` один ресурс с loader `async () => 'same'` был последовательно загружен для `'a'` и `'b'`; сохранён снимок `'a'`, подключён `persist`, затем вызван `restore(snapshotA)` после `'b'`. Вывод: `{"before":4,"after":4,"wakes":0,"oldKey":"\"b\"","savedKey":"\"b\"","liveKey":"\"a\""}`. То есть актуальный `snapshot().key` уже `'a'`, но storage всё ещё рекламирует `'b'`. В отдельной пробе новый ресурс был подключён к этому же storage: `fresh.suspend('b')` вернул `'same'`, `fresh.suspend('a')` бросил Promise и вызвал loader с аргументом `'a'` (`aSuspended true calls [\"a\"]`). Идентичные байты нужны для равенства live-полей и не отменяют неправильный маршрут ключа.

**Исправление/приёмка.** Wire-идентичность ресурса должна участвовать в сигнале изменения, не добавляя `key` в публичный live `IResourceData`: при отличающемся ключе поднять версию и уведомить наблюдателей/сериализаторов, сохраняя точность обычных одинаковых restore. Проверить снимки с одинаковыми четырьмя полями и различными ключами (Success и Error), `getVersion`, wildcard subscription, persist default/coalesce и DevTools `send`/cache; не требовать уведомления при полностью одинаковом снимке. Отличается от R11-04: обычная сериализация уже **содержит** ключ, но здесь запись вообще не запускается.

## R12-API-03 — P2 — Comparator не включён в ключ снимка React selector-хука

**[INFERENCE], без runtime-пробы.** `useCarburetorValue` хранит `cache.current = {carburetor, select, version, value, filled}` и возвращает `entry.value`, если совпали только store/selector/version (`lib/src/Interop/useCarburetorValue.ts:12-18,206-214,233-249`); аргумент `isEqual` в ключ не входит. Даже когда `isEqual` меняется и `getSnapshot` получает новую identity из-за `[carburetor, select, isEqual, recordRead]`, эта проверка срабатывает раньше нового вызова selector/comparator. Допустимый comparator может сохранить старое значение при изменившемся состоянии (документировано на `:114-120`), а новый строгий comparator так и не получит шанса сравнить.

**Минимальный сценарий.** Стабильный `select = data => data.title`. Монтировать компонент с `isEqual = () => true` при `title='old'`; `store` меняется на `'new'`: подписка будит hook, но прежний comparator сохраняет `'old'`, а cache получает новую версию. Родитель меняет **только** prop `isEqual` на `Object.is` и перерисовывается; версия/source/selector остались прежними, поэтому `getSnapshot()` возвращает `'old'` навсегда до следующего изменения store. Тесты с custom comparator проверяют неизменную функцию (`__tests__/Engine/Tooling/InteropDefaultComparator.test.tsx:93-120`), а тесты смены selector не покрывают смену comparator.

**Исправление/приёмка.** Учитывать identity comparator в валидности cache либо переоценивать текущую selection при его смене, при этом сохранение исходной ссылки при действительно равных значениях и синхронизация новых reads остаются обязательны. Проверить смену always-equal → строгий comparator после подавленного изменения, обратную смену, переключение source/selector и отсутствие дополнительных подписок.

## R12-API-04 — P2 — `persist` не сообщает ошибку `getItem` в `onError`

**Механизм.** В JSDoc `persist` сказано, что неудачная загрузка/запись передаётся `onError`, а `IPersistOptions.onError` документирован для нечитаемого storage (`lib/src/Carburetor/Tooling/persist.ts:5-16`; `lib/src/Carburetor/Models/Tooling.ts:23-28`). Однако `storage.getItem(key)` расположен **вне** `try` (`persist.ts:18-23`); `removeItem(key)` внутри `catch` также не изолирован от ошибок (`:23-30`). Ограниченный/отключённый browser storage вправе выбросить на чтении; подключение сразу прерывается, `onError` не вызывается и disposer не возвращается.

**Реальный smoke.** `persist(new Carburetor({n:0}), {key:'x', storage:{getItem(){throw Error('storage unavailable')},setItem(){},removeItem(){}}, onError:e => errors.push(e.message)})` вывел `thrown storage unavailable` и `reported []`. Это не недействительный JSON: даже попытка прочитать storage не достигла общего обработчика.

**Исправление/приёмка.** Обрабатывать исключения `getItem` и удаление повреждённого значения так, чтобы `onError` получил исходную причину и разрешённая политика продолжения/отключения persistence была явной; обычные synchronous writes и disposer сохранить. Сценарии: исключение чтения, некорректный JSON с падающим `removeItem`, успешное чтение и ошибка `setItem`; проверить доставку в `onError`, отсутствие ложных записей и судьбу подписки. Не маскировать сбой пустым fallback без уведомления.

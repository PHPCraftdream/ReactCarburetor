## R28-ENG-01 — invalidating an admitted readonly cache entry throws and can partly invalidate a bulk operation (P2)

**Public contract and precise source.** `README.md:554-563` promises that `ResourceCache.invalidate(args)` marks an entry stale without fetching, and `invalidateAll()` re-arms entries; `:916-924` admits own enumerable string-keyed **data** properties without requiring writable descriptors. `:671-694` promises owned history that retains supported readonly endpoint descriptors, rather than flattening them like ordinary public snapshots. `:656-658` distinguishes writable *operational* replacement from direct draft writes: a request after readonly replay can operate while a direct attempted draft write still refuses the readonly field. Here the consumer calls the public cache operation, not a direct draft assignment. A complete entry returned from exported `getInitialCacheEntry()` remains a supported state when its own enumerable `invalidated` data field is readonly. The accepted, value-changing `setData` and history undo/redo below prove this field is actually retained as readonly in the current endpoint.

`lib/src/Carburetor/Resource/Cache/ResourceCacheLifecycle.ts:168-204` implements both invalidation operations by writing `draft.entries[key].invalidated = true` and `draft.entries[key].failed = false` in `this.update`, without checking or preparing writable lifecycle capabilities. `Store/Tracking/createWriteProxy.ts:227-268` reaches a native `Reflect.set` that refuses an effective write to this non-writable data field. In contrast, `Resource/Cache/State/prepareCacheRequest.ts:17-46` prepares a separate operational graph for restricted request fields, but only from `fetch()`, not from `invalidate`/`invalidateAll`. Thus a legitimate cache entry can load/refresh after readonly replay but cannot be explicitly marked stale. In a bulk call, `update`'s finally-publication (`Store/Carburetor.ts:422-439`) publishes earlier entry changes despite the later rejection.

**Expected versus observed.** After successful undo/redo, `invalidate('a')` should finish, mark the *current operational entry* `invalidated:true`/`stale:true` without starting a loader, and leave the held readonly history endpoint untouched so replay still preserves its descriptor. Instead it throws `TypeError`; the accepted current entry remains fresh and cannot be explicitly re-armed. This is not a request to make a direct draft assignment to a readonly field legal or to notify for a descriptor-only metadata change: the attempted change is the entry's actual boolean state value through the documented invalidation API.

The same underlying issue makes **bulk** invalidation partly land, not merely fail before work. Complete bounded source command:

Expected: all admitted entries become invalidated with one successful publication, without fetching. Observed: the first changes, the second does not, the operation throws, and version advances. **Repair direction:** prepare writable capabilities for the affected operational entry fields before applying single/bulk invalidation, preserving owned history endpoints, native aliases/backlinks, raw failure ownership and unaffected entries. For bulk, prepare all necessary replacements before the first entry mutation/publication; keep ordinary direct-draft readonly refusal and strict history admission intact. Avoid masking the exception while retaining an uninvalidated entry.

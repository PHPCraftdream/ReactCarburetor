## R13-API-01 — P2 — Cache replacement retains the old raw failure for a surviving key

**Code and contract.** `ResourceCache` inherits public `Carburetor.setData(data)`, whose advertised behavior is replacement (`lib/src/Carburetor/Store/Carburetor.ts:150-186`). The cache's `didSetData()` reconciles eviction and views, but deletes an entry from `failures` *only when its key disappears* (`lib/src/Carburetor/Resource/Cache/ResourceCache.ts:69-84`). A failed loader saves the actual rejection in `failures` (`ResourceCacheLifecycle.ts:576-596`); `suspend(args)` prefers this saved rejection over the current entry's `error` (`:400-414`). Replacing an Error entry at the **same key** with a different snapshot therefore presents the new error in `getEntry` but throws the prior request's unrelated raw error. Replacement with Success also leaves `getFailure(args)` reporting an obsolete failure. By contrast, `fromJSON`/`restore` clears the map (`ResourceCacheLifecycle.ts:59-68`), so this is the public direct-replacement route, not an already-fixed restore race.

**Executed source probe.** An async loader rejected with `const old = new Error('old-raw')`. After `await cache.load('x')`, the caller performed `cache.setData({entries: {[cache.keyOf('x')]: {...cache.getData().entries[key], error: 'replacement-message', failed: true}}})`. Output: `setData {"entry":"replacement-message","thrown":"old-raw","identical":true}`; `cache.suspend('x')` threw exactly `old`. Feeding that same replacement through `cache.fromJSON(next)` instead printed `{"entry":"replacement-message","thrown":"replacement-message","identical":false}`. Expected for `setData`: the new entry's failure message, not the previous request's raw rejection. A UI using Suspense/error boundaries can display the wrong cause after a public cache replacement.

**Fix acceptance:** reconcile raw failures when replacing surviving keys (not merely removed keys), without discarding a genuinely current in-flight failure on unrelated entry replacement. Exercise Error→different Error, Error→Success, same-key pending request and `setData`/`restore`/`fromJSON` controls; assert `getEntry`, `getFailure` and what `suspend` actually throws.

## R13-API-02 — P2 — Invalidation cannot re-arm a first-load Error for `useResource`

**Code and contract.** `IResourceEntry.failed` explicitly says `invalidate`/`invalidateAll` clear the flag so entries whose last attempt failed refetch on the next render (`lib/src/Carburetor/Models/Resource.ts:48-61`); `docs/promise-cache.md:96-100` likewise calls invalidation a re-arm. Both invalidation methods set `invalidated = true` and `failed = false`, *without changing Error status* (`ResourceCacheLifecycle.ts:182-210`). But `AntiHookComponent.useResource` queues a post-commit load only if `view.status !== EResourceStatus.Error` (`lib/src/Carburetor/Component/AntiHookComponent/Reads.tsx:221-257`). After a first-load rejection, the mounted reader renders Error and remains Error forever after `invalidate('a')` or `invalidateAll()` despite the explicit fresh external event; there is no queued load to settle. The condition is necessary to avoid retrying on the failure's **own** notification, but it also blocks the later explicit invalidation. A previously successful entry whose refresh fails remains Success, so it takes a different route.

**Executed mounted React probe.** `new ResourceCache(async () => { calls++; throw Error('network'); })`, a mounted `AntiHookComponent` rendering `this.useResource(cache, 'a').status + ':' + failed`, React `act` and a JSDOM root: after the first settled failure the DOM/call count was `error:true 1`. Following `await act(async () => cache.invalidate('a'))` it was `error:false 1`. Expected under the documented invalidation/re-arm contract: another request is started after that commit; actual: no second loader call. The README's advice to call explicit `refresh` to retry a failure (`README.md:547`) works around this, but conflicts with the explicit invalidation contract in the model and cache design notes. The two policies need one consistent documented behavior, with the actual supported `invalidate` behavior implemented accordingly.

**Fix acceptance:** a failed initial load stays quiet after its own rejection, while a *later* explicit `invalidate`/`invalidateAll` with an active reader starts exactly one retry after commit. Keep failed-refresh Success behavior, no retry in render, explicit `refresh`, and the Error boundary/Suspense paths intact. Check DOM/status, loader calls and subscription cleanup, not only flags.

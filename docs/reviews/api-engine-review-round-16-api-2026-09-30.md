## R16-API-01 — keyless whole-state replacement borrows the last settled request's key

**Contract and mechanism.** `ResourceCarburetor` is a public subclass of `Carburetor`, so `setData(IResourceData<T>)` is public (`Models/Store.ts:81-99`, `Resource/ResourceCarburetor.ts:38-76`). Its documented `snapshot` and `serialize` couple data to the key for which it settled (`ResourceCarburetor.ts:91-103`); `suspend` serves a Success only when that private `settledKey` equals the requested key (`:219-238`). `start` clears `settledKey` for a new request (`:318-350`), and keyed `restore` explicitly installs a key before the new state (`:111-161`). But the inherited `Carburetor.setData` adopts the caller's **keyless** data and calls `didSetData` (`Store/Carburetor.ts:153-180`), which only reconciles the raw error (`ResourceCarburetor.ts:173-203`); it never invalidates `settledKey`. After loading key `'a'`, replacing its Success with `{status:Success,data:'injected',updatedAt:3}` makes `suspend('a')` synchronously return `'injected'` without a loader invocation, and wire `snapshot()` attributes `'injected'` to `key:'"a"'`. This is not a stale-render issue: a direct imperative read gets the wrong answer. Consumers caching per-argument results or hydrating this wire state can serve injected data as if it came from that request. Unlike the already-fixed R15 same-message raw Error ownership, this is **settled-key** ownership of a newly adopted Success.

**Executable actual-source proof.** Run from this worktree (Bun 1.4.2):

```sh
bun -e "import {ResourceCarburetor,EResourceStatus} from './lib/src/Carburetor/index.ts';let calls=0;const s=new ResourceCarburetor(async (a:string)=>{calls++;return 'network:'+a});await s.load('a');s.setData({status:EResourceStatus.Success,data:'injected',error:undefined,updatedAt:3});console.log(JSON.stringify({served:s.suspend('a'),calls,wire:s.snapshot()}))"
```

Observed `{"served":"injected","calls":1,"wire":{"status":"success","data":"injected","updatedAt":3,"key":"\"a\""}}`. A same-version mixed-format package probe (ESM `ResourceCarburetor`, CJS `EResourceStatus`, ESM history) also returned `'manual'` from `suspend('a')` with only one loader call and produced a snapshot carrying the old key; ESM history undo/redo followed the misattributed wire state. **Controls:** `setData(s.getData())` with the identical object continued serving its own original answer, and `restore(savedKeyedSnapshot)` / `fromJSON(savedKeyedSnapshot)` continued serving the explicitly keyed answer. The repair must preserve those paths and must not invent a key for keyless data; reconcile key ownership before synchronous subscribers observe the replacement, without destroying the key deliberately installed by keyed restore.

## R16-API-02 — draft replacement preserves an obsolete cache rejection

**Contract and mechanism.** A keyed cache carries serializable `IResourceEntry.error` plus the raw failure returned by `getFailure(args)` and thrown by `suspend(args)` (`Models/Resource.ts:27-63`; `Resource/Cache/ResourceCache.ts:286-294`, `ResourceCacheLifecycle.ts:388-415,555-598`). `ResourceCache.setData` already compares old and new **entry object identities** and clears failures before publication when they differ (`ResourceCache.ts:76-107`). But normal subclass `update(draft => { draft.entries[key] = freshEntry })` goes through `preEmit`, which sees the precise whole-entry path (`:109-169`), and `reconcileFailure` only compares `status` and `error` strings (`:128-139`). It ignores the changed owning entry identity. A new Error entry carrying the same message and changed timestamp retains the unrelated former loader rejection even inside a synchronous subscriber. The public base's `update` is a documented protected subclass mutation API (`Store/Carburetor.ts:445-462`), and the resource design expressly claims subclass `draft`/`update` reconciliation (`docs/promise-cache.md:121-124`): this is a supported path, not mutation of the raw `getData()` object. A mounted error boundary receiving `suspend` gets an older request's raw error, rather than the new entry's reconstructed serializable error.

**Executable actual-source proof.** Run from this worktree:

```sh
bun -e "import {ResourceCache} from './lib/src/Carburetor/index.ts';const old=new Error('denied');class C extends ResourceCache<number,string>{replace(k:string){this.update(d=>{d.entries[k]={...d.entries[k],updatedAt:5}})}}const c=new C(async()=>{throw old});await c.load('a');c.replace(c.keyOf('a'));let thrown=false;try{c.suspend('a')}catch(e){thrown=e===old}console.log(JSON.stringify({timestamp:c.getEntry('a').updatedAt,keepsOldRaw:c.getFailure('a')===old,throwsOldRaw:thrown}))"
```

Observed `{"timestamp":5,"keepsOldRaw":true,"throwsOldRaw":true}`. The same failure was observed against both the actual TypeScript source and a packaged mixed-format consumer (CJS cache plus ESM package loaded). **Discriminating controls:** changing *only* an existing entry's `updatedAt` via `draft.entries[k].updatedAt = 4` retained its legitimate raw rejection, while adopting a distinct entry through public `setData({entries:{[k]: ...}})` cleared it. Identity ownership should be reconciled for a replaced entry on the draft write path too, preserving unchanged-entry and unrelated-path failures; avoid clearing all failures on every write.

## R16-API-03 — a delayed pre-clear mutation resurrects history

**Contract and mechanism.** `clear()` promises to forget history **while keeping the current state** (`Tooling/CarburetorHistory.ts:142-146`). History receives patches at mutation time, before its publication callback is scheduled on the store's `IUpdateScheduler` (`:64-95,153-198`; `Store/Transaction/PatchObserverRegistry.ts:126-157`). A throttled scheduler is public and supported (`Store/Scheduling/ComponentUpdateThrottle.ts:14-15,43-80`); synchronous state writes can consequently precede their history publications. `clear()` only assigns fresh `past` and `future` arrays, without clearing `pendingPatches`, `pendingOpaque`, the scheduled publication or resetting the baseline. If the store is already `x=1` when `clear()` is called, delivery of its pending pre-clear patch subsequently adds a past operation; `undo()` reverses it to `x=0` despite the explicit clear at `x=1`. This also affects tooling that offers a reset-history action during a coalescing window. No generic retry/revalidation feature is implicated.

**Executable actual-source proof.** A deterministic public scheduler below models the coalescing delivery boundary without waiting for a timer:

```sh
bun -e "import {Carburetor,CarburetorHistory} from './lib/src/Carburetor/index.ts';class Scheduler{q=new Map<string,()=>void>();schedule(id:string,fn:()=>void){this.q.set(id,fn)}cancel(id:string){this.q.delete(id)}flush(){const jobs=[...this.q.values()];this.q.clear();jobs.forEach(fn=>fn())}}class S extends Carburetor<{x:number}>{bump(){this.update(d=>{d.x++})}}const schedule=new Scheduler(),store=new S({x:0},schedule),history=new CarburetorHistory(store);store.bump();history.clear();const immediate=history.canUndo();schedule.flush();const late=history.canUndo();const reversed=history.undo();console.log(JSON.stringify({immediate,late,reversed,x:store.getData().x}));history.disconnect()"
```

Observed `{"immediate":false,"late":true,"reversed":true,"x":0}`. An actual packaged reverse-format probe (ESM `Carburetor` + CJS `CarburetorHistory`, `ComponentUpdateThrottle` subclass with an explicit flush) yielded the identical result. A correct clear boundary must discard mutations already made before clear, reconcile its baseline to the **current** state and still record subsequent writes, including when a scheduler coalesces the old and new publications. Do not simply drop *all* deferred future changes.

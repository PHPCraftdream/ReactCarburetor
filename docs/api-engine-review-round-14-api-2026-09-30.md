## R14-API-01 — P2 — A request started before invalidation can consume that invalidation

**Mechanism / contract.** `ResourceCacheLifecycle.invalidate()` and `invalidateAll()` set `invalidated=true` on an existing entry, but neither aborts an in-flight request (`lib/src/Carburetor/Resource/Cache/ResourceCacheLifecycle.ts:184-212`). The request that started *before* the invalidation remains current, and its `settleSuccess()` unconditionally sets `invalidated=false` and replaces the data with its earlier response (`:517-552`, especially `:541-549`). `load()` then treats the newly stamped Success as fresh (`:143-155`, `:277-283`). This defeats the stated use case “invalidate after a write the server accepted” (`docs/promise-cache.md:99-100`; `README.md:545-551`): a response representing server state *before* that write cannot satisfy the later invalidation. This is not the R13 repair of invalidating an **already failed** entry; the entry here is Pending, and there is no raw-error replacement or abort.

**Executed cache and mounted-reader source probes.** With `ttl: Infinity`, first `load('a')` blocked on a controlled promise representing server value `old`. While Pending, `invalidate('a')` set `invalidated:true`; the simulated server advanced to `new`, then that first promise resolved `old`. Calling `load('a')` again returned without invoking the loader: output was `{"calls":1,"entry":{"status":"success","data":"old","invalidated":false,"failed":false,"stale":false}}` (timestamp omitted). With a mounted `AntiHookComponent` rendering `useResource(cache,'a')` under React/JSDOM and `act`, the actual DOM/call-count transition was `pending:true:undefined / 1` → after invalidation `pending:true:undefined / 1` → after old answer `success:false:old / 1`; another explicit `load` kept `success:false:old / 1`. Expected: the post-invalidation entry still requires a post-invalidation answer, and a mounted reader eventually observes `new` rather than settling forever on the pre-write answer. The invalidation itself must still not fetch eagerly or write during render.

**Acceptance.** Retain request/invalidation ordering per key so an older success cannot clear newer invalidation; cover Pending initial load and Success refresh, `invalidate` and `invalidateAll`, both settle outcomes, repeated `load` and mounted-reader postcommit rendering. Preserve pre-R14 abort/retry ownership and unrelated-key in-flight requests; do not silently convert every invalidation into an immediate fetch.

## R14-API-02 — P2 — Single-slot `setData` leaves the previous rejection attached to a replacement Error

**Mechanism / contract.** Public `ResourceCarburetor` inherits `Carburetor.setData`, documented as a whole-state replacement (`lib/src/Carburetor/Store/Carburetor.ts:150-186`; `Models/Store.ts:81-99`). The slot's successful/error settlements and `restore()` reconcile `lastError`/`hasLastError` (`ResourceCarburetor.ts:134-156,389-431`), but inherited `setData` does not. `suspend('a')` for a stored Error preferentially throws the raw previous `lastError` if `settledKey` still equals `'a'` (`:183-195`). Replacing that Error with a *new Error at the same key* updates the subscribed serializable state and wire message but leaves `getLastError()` and `suspend()` reporting the old request. This is the single-slot counterpart of the now-fixed R13-API-01 **keyed-cache** replacement, not a claim that keyed cache still fails.

**Executed source probes.** Loader for `'a'` rejected `Error('old rejection')`; after `await r.load('a')`, `r.setData({...r.getData(), error:'new replacement error', status:EResourceStatus.Error})` produced `{"live":{"status":"error","error":"new replacement error"},"raw":true,"thrown":"old rejection","identity":true}` (`raw`/`identity` compare to the original Error). The control `r.restore({...r.snapshot(),error:'restored error'})` instead threw `restored error`, not the old object. A connected default `persist` storage recorded `{"status":"error","error":"access-denied","key":"\"a\""}` after public replacement, while `getLastError().message` and `suspend('a')` still said `transport-down`. A Suspense error boundary therefore displays a different failure than the visible and persisted slot. Timestamps were omitted from these output excerpts; the observed message/object identity is the invariant.

**Acceptance.** On public single-slot replacement, synchronize the raw rejection with the installed Error/Success state **before synchronous publication**, without discarding a still-current in-flight request for an unrelated operation. Test Error→different Error, Error→Success, untouched previous Error, and `restore`/`fromJSON` controls; compare `getData`, `snapshot`/`serialize`, `getLastError` and actual `suspend` throw. No invented argument key should be inferred from keyless `IResourceData`.

## R14-API-03 — P2 — A cache used only via `suspend` never refetches invalidated settled entries

**Mechanism / contract.** `ResourceCacheLifecycle.suspend()` returns every stored Success regardless of `entry.invalidated`/TTL and rethrows every stored Error regardless of `entry.invalidated`/its explicitly cleared `failed` flag (`ResourceCacheLifecycle.ts:390-414`). The only fetch from this method is for a miss/non-settled entry. `invalidate` re-arms failed entries and marks successes stale (`:184-212`; `Models/Resource.ts:40-61`). The design contract says an invalidation does not immediately fetch, but entries being read refetch on their **next read** (`docs/promise-cache.md:92-105`); `README.md:557-559` exposes `suspend(args)` as the per-entry Suspense read. The R13 mounted `useResource` fix checks invalidated Error inside `Reads.tsx:221-242`, so that bridge can retry, but a consumer using only `cache.suspend(args)` in a Suspense/error-boundary render never reaches that bridge. This is independent of R14-API-01: no request is in flight when invalidation occurs here.

**Executed source probes.** A Success cache with `ttl: Infinity` loaded `'x'` once, then `invalidate('x')` and repeated `suspend('x')`/`invalidateAll()` returned `'1'` each time, loader `calls:1`, while `getEntry('x')` stayed `stale:true, invalidated:true`. A different cache failed its first load with `offline`; `invalidate('a')` yielded `status:error, invalidated:true, failed:false`, yet `suspend('a')` threw the old `offline` Error (not a Promise) and loader `calls:1`. An explicit `load('a')` recovered on call 2, demonstrating the loader and re-arm state were otherwise usable. Expected for a Suspense-only reader after an explicit re-arm: its next read can arrange the request/deferred publication and ultimately return the new answer (or throw its in-flight Promise); it must not retry the same failure just because the failure rendered again. For Success, retaining visible data during a refresh is compatible with this expectation; the defect is the *absence of any refresh*.

**Acceptance.** Exercise `suspend`-only React Suspense/error-boundary consumers with explicit invalidation, TTL-expired Success, Error after explicit invalidation, no-auto-loop after a rejection, and cleanup. Preserve the cache's stale-while-revalidate Success presentation and the rule against notifying subscribers in render; do not fix this by fetching from `invalidate` itself. Align any intentional alternate `suspend` policy with the explicit next-read public contract if one is chosen.

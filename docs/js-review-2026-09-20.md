# JavaScript/TypeScript review — 2026-09-20

Reviewed revision: `a49ddf2` on `master`.

## Assessment

React Carburetor has a useful central idea: make a component depend on the state fields it reads, and stop unchanged props from propagating parent renders. This can substantially reduce work in interfaces with many independently changing rows, cells, or panels. Keeping domain actions in stores and handlers on component instances also makes some code easier to follow.

The current implementation is not ready to promise reliable updates across its advertised API. Small, ordinary examples lose subscriptions, retain obsolete values, return another resource's answer, or repeatedly refetch after an error. Correctness needs priority over additional features or finer performance tuning.

The benefit comes from subscription granularity, update propagation, and component boundaries. Removing hooks alone does not demonstrate a performance improvement. The repository's benchmark measures subscription matching; it does not compare complete React applications or measure interaction latency.

## Scope and method

Reviewed the JS/TS state engine, class component integration, interop entry point, resource/cache implementation, scope and tooling, representative JS lint rules, tests, documentation, demo logic, and package/build configuration. Rust/native implementation was outside scope.

Source files were read only. This report is the only repository file created for the review. Existing changes were excluded from the report commit.

Findings marked **reproduced** were exercised with small, bounded Node programs passed through standard input. They imported current TS sources using in-memory type transformation and alias resolution; type-only imports were removed by the loader. React checks used the installed React 19.3.0, React DOM, and JSDOM with `act`. Lint checks used ESLint's in-memory `Linter.verify`. No source or test fixtures were written, no build or full test suite was run, and no benchmark or stress workload was executed. This is targeted defect verification, not a claim that the existing suite passes or fails.

P1 means a correctness issue to address before relying on the affected feature in production. P2 means a narrower correctness issue or a material reliability/performance problem. Suggested fixes below are design directions, not implemented patches.

## What works well conceptually

- Explicit store methods give business operations a clear home. `update(draft => ...)` is a convenient mutation API.
- Leaf subscriptions and the subscriber index avoid scanning every component for every write.
- The props/state gate addresses parent-induced renders, an important complement to store subscriptions.
- The main component API does not install subscriptions during render.
- Scoped construction, resource cancellation, per-entry cache subscriptions, and an opt-in interop entry point address real integration needs.
- Effect cleanup, diagnostics, lint rules, and published-package tests show attention to failure modes, not just the demo's happy path.

These strengths are worth preserving while repairing the invariants below.

## Confirmed findings

### R01 — P1: StrictMode leaves class components unsubscribed

**Reproduced.** Mount a component that reads `store.n` under root-level `StrictMode`, then increment `n`. After mounting, the store has zero subscriptions. Its value becomes `1`, while the DOM continues to show `0`.

[AntiHookComponent.tsx](../lib/src/Carburetor/Component/AntiHookComponent.tsx#L60) subscribes in `componentDidMount`; [releaseSubscriptions](../lib/src/Carburetor/Component/AntiHookComponent.tsx#L242) then clears the tracked reads. The subsequent mount lifecycle has nothing left to restore. React documents this mount/unmount/mount check in development in its [class lifecycle reference](https://react.dev/reference/react/Component#componentdidmount).

Preserve the committed dependency description independently from active subscription handles, and make subscription setup/cleanup replayable. Add a root StrictMode regression covering ordinary stores, computed values, and cache readers. Verify Suspense hide/reveal separately rather than assuming the StrictMode repair covers it.

### R02 — P1: Computed values become stale, including permanently wrong composed results

**Reproduced, two cases.**

1. Read an unobserved computed `read(store).n * 2` at `n = 1`; change `n` to `2`; read again. It returns `2`, not `4`. Attaching the first subscriber still returns `2`.
2. Create `left = n * 2`, `right = n * 3`, and `sum = left + right`; subscribe to `sum`; change `n` from `1` to `2`. The subscriber observes `7`, and `sum.get()` remains `7` instead of `10`.

[Computed.ts](../lib/src/Carburetor/Derived/Computed.ts#L38) treats `valid` as sufficient even when no dependency subscription has existed to invalidate it. [Dependency replacement](../lib/src/Carburetor/Derived/Computed.ts#L110) unsubscribes the entire previous graph, including dependencies that remain in use. In the diamond example, evaluation sees one refreshed and one old input; releasing and reobserving dependencies then refreshes an input without correcting the already-produced outer value.

Separate invalidation from evaluation, validate dependency versions for unobserved reads, and update dependency edges without tearing down retained edges. Define propagation ordering so observers see a settled graph. Also address batching across multiple source stores: a computed depending on two stores was evaluated twice in one transaction.

### R03 — P1: Interop cache ignores selector and store identity

**Reproduced.** Render `useCarburetorValue(store, d => d.a)`, then change the selector to `d => d.b` without a store write. The result remains `a`. Switching to a different store at the same version also returns the previous store's value.

[useCarburetorValue.ts](../lib/src/Interop/useCarburetorValue.ts#L37) keys its shared ref cache only by the numeric version. Recreating `getSnapshot` for a new store or selector does not invalidate the ref.

Make snapshot caching sensitive to source and selector changes and define comparator changes explicitly. Avoid letting work from an abandoned render overwrite the committed selector's cache.

### R04 — P1: Interop does not update conditional selector dependencies

**Reproduced.** A stable selector `d => d.which ? d.a : d.b` initially records `which,a`. Switching `which` to false displays `b`, but the subscription remains `which,a`. A later change to `b` does not update the DOM.

[useCarburetorValue.ts](../lib/src/Interop/useCarburetorValue.ts#L23) tracks reads only when the subscription is installed; later snapshot evaluations discard read paths. A stable selector function does not imply a stable dependency set.

Reconcile tracked dependencies when selector evaluation changes them, with a version check around subscription installation. Include the case where the selected value stays equal while the dependency branch changes.

### R05 — P1: Object-valued interop selectors are neither reactive nor immutable snapshots

**Reproduced.** Use `d => d.user`, and render `user.name`. Change `user.name` from `Ann` to `Bob`. The subscription has an empty read set and the DOM stays `Ann`. Meanwhile the previously returned snapshot now reads `Bob`.

The [selector subscription](../lib/src/Interop/useCarburetorValue.ts#L25) does not read any leaf when a selector returns an object. The returned read proxy still points at mutable backing data.

Define and implement a safe contract for selectors returning branches. It needs both a dependency on the selected branch and a stable, immutable snapshot representation. Simply using `useSyncExternalStore` does not supply either guarantee; React explicitly requires immutable snapshots for mutable external stores in its [external-store reference](https://react.dev/reference/react/useSyncExternalStore#im-getting-an-error-the-result-of-getsnapshot-should-be-cached).

### R06 — P1: Read tracking misses object presence and other valid object relationships

**Reproduced.**

- Reading `!!data.user` when `user` is an object records no paths. Replacing it with `null` notifies nobody.
- With `{a: shared, b: shared}`, reading `b.n` and writing `draft.a.n` changes the rendered value's backing object without notifying its subscriber.
- A plain object getter `get doubled() { return this.n * 2; }` records `doubled`; changing `n` does not notify that reader.

The first problem follows from treating every object-valued access as traversal in [createReadProxy.ts](../lib/src/Carburetor/Store/Tracking/createReadProxy.ts#L23). A proxy cannot later intercept an ordinary truthiness test. Aliases are tracked by access path, not target identity. Accessors run with the raw object as receiver because `Reflect.get` omits the proxy receiver.

Add branch replacement/presence dependencies without turning every nested read into a whole-store subscription. Specify whether shared references and accessors are supported; implement tracking for them or reject unsupported shapes in development. “Plain objects and arrays” is currently too broad a statement of the supported data model.

### R07 — P1: The read-only boundary can silently mutate state

**Reproduced.** Both of these change state without a version increment or notification:

```js
Object.defineProperty(store.read(() => {}), 'value', {value: 2});

const view = store.read(() => {});
Object.getOwnPropertyDescriptor(view, 'user').value.name = 'changed';
```

[createReadProxy.ts](../lib/src/Carburetor/Store/Tracking/createReadProxy.ts#L55) rejects assignment and deletion but leaves property definition and descriptor access unguarded. Prototype mutation and preventing extensions also need an explicit policy.

Complete the read-only boundary, including descriptor escape paths, while respecting proxy invariants. Frozen objects need attention too: reading a nested object through a frozen root currently throws because the proxy returns a different value for a non-configurable, non-writable property. This restriction comes from the [ECMAScript proxy invariants](https://tc39.es/ecma262/multipage/ordinary-and-exotic-objects-behaviours.html#sec-proxy-object-internal-methods-and-internal-slots-get-p-receiver).

The separately documented pass-through treatment of Map/Date/class instances also means “deeply read-only” needs qualification even after ordinary-object traps are fixed.

### R08 — P1: A failed stale refresh automatically starts another request

**Reproduced with a mounted component.** Load an entry successfully, read it with `useResource`, invalidate it, and reject the refresh. A third loader call starts automatically, despite the documented absence of automatic retries. The reproduction deliberately left that third request unresolved to keep the check bounded.

[useResource](../lib/src/Carburetor/Component/AntiHookComponent.tsx#L119) skips entries with status `Error`. However, [settleFailure](../lib/src/Carburetor/Resource/Cache/ResourceCache.ts#L425) keeps an entry with old data in `Success`, clears `refreshing`, and leaves it stale. Its notification triggers the same fetch condition again. Repeated failures can sustain a request/render loop.

Track failed attempts independently of the last successful data status. Allow retries only on an explicit refresh or a defined new invalidation policy. Cover initial failure and refresh failure as different cases.

### R09 — P1: Single-slot Suspense returns data for the wrong arguments

**Reproduced.** After `await resource.load('a')`, calling `resource.suspend('b')` returns the answer for `a`.

[ResourceCarburetor.suspend](../lib/src/Carburetor/Resource/ResourceCarburetor.ts#L42) returns success or throws a stored error before checking the requested key. A component whose ID prop changes can keep showing another record.

Associate settled success/error state with its argument key. Resolve the requested identity before returning a value or throwing an error, and start/suspend for a different key.

### R10 — P1: Hydration token IDs depend on unrelated initialization order

**Reproduced in two independent Node processes.** The server creates one unrelated store before declaring its token; the client declares the same logical token without that extra store. The server serializes value `42` under `carburetor-uid-2`; the client looks for `carburetor-uid-1` and silently starts at `0`.

[carburetorToken.ts](../lib/src/Carburetor/Component/Scope/carburetorToken.ts#L4) uses the same [process-local counter](../lib/src/Carburetor/Store/Utils/getUid.ts#L1) as stores and components. [hydrate](../lib/src/Carburetor/Component/Scope/CarburetorScope.ts#L54) relies on matching those IDs.

Use an explicit stable serialization key, distinct from runtime instance IDs. Validate duplicate keys and mismatched payloads. Existing scope tests reuse the same token object for server and client, so they cannot establish correctness across independently initialized bundles.

### R11 — P2: Cache bounds are not enforced after requests finish

**Reproduced.** With `maxEntries: 1`, launch three distinct requests before any finishes and await all three. The cache retains three entries with zero pending requests.

[evict](../lib/src/Carburetor/Resource/Cache/ResourceCache.ts#L246) runs when a request starts and exempts pending requests. [Settlement](../lib/src/Carburetor/Resource/Cache/ResourceCache.ts#L396) never enforces the bound again. Likewise there is no eviction pass when a retained entry loses its final subscriber.

There is a second growth path: [getEntry](../lib/src/Carburetor/Resource/Cache/ResourceCache.ts#L89) inserts access metadata for missing keys. Three reads of absent entries increased `lastUsed` by three without adding cache entries. Eviction only enumerates actual entries.

Enforce a documented soft bound after settlement/release, and avoid retaining metadata for nonexistent entries. Use a retention index if cache and subscriber counts make full scans costly.

### R12 — P2: Cache eviction breaks Suspense's deferred-notification guarantee

**Reproduced.** Fill a cache with one entry at `maxEntries: 1`, subscribe, then call `suspend` for another key. The subscriber runs synchronously inside the `suspend` call.

[fetch](../lib/src/Carburetor/Resource/Cache/ResourceCache.ts#L333) defers `markLoading` notification but immediately invokes `evict`. Eviction calls `update`, publishing both deletion and accumulated loading writes during render.

Defer every externally observable publication in the Suspense path, including eviction. Test a full cache with an existing mounted reader, not just the first request into an empty cache.

### R13 — P2: Mutation errors and mixed write paths can leave observers behind

**Reproduced, two cases.**

- An `update` callback writes `value = 1` and throws. State changes, but the version remains zero and subscribers are not notified.
- A callback changes `draft.a` and directly changes `store.getData().b`. Only the `a` subscriber runs. The documented whole-store fallback for untracked mutation does not run.

[update](../lib/src/Carburetor/Store/Carburetor.ts#L167) publishes only after normal return, even though mutation is immediate. [emitUpdate](../lib/src/Carburetor/Store/Carburetor.ts#L227) can infer a coarse write only when no tracked writes are present.

Define exception semantics: roll back changes, or publish partial changes before rethrowing. For direct mutation, choose an enforceable contract: prohibit it, require an explicit coarse publication API, or instrument it. Do not promise automatic detection of mutations that bypass all tracking. A `preEmit` helper touching draft can also defeat the assumed fallback.

### R14 — P2: A subscriber exception can interrupt delivery; throttling can remain stuck

**Reproduced with persistence and an explicitly invoked throttle flush.**

A storage `setItem` throwing a quota error bypasses `persist`'s `onError` and interrupts notification before a later UI subscriber runs. The data has already changed.

[Persist](../lib/src/Carburetor/Tooling/persist.ts#L10) only catches initial restore errors. [notifyWrites](../lib/src/Carburetor/Store/Carburetor.ts#L126) directly invokes scheduled callbacks without isolating their failures. [UpdateBatch.flush](../lib/src/Carburetor/Store/Transaction/UpdateBatch.ts#L45) can similarly abandon the rest of a drained batch.

[ComponentUpdateThrottle](../lib/src/Carburetor/Store/Scheduling/ComponentUpdateThrottle.ts#L45) clears its queue before calling callbacks and resets its timer only after all return. A throwing callback loses later callbacks and bypasses timer cleanup. The probe confirmed the remaining batch was skipped and the timer flag stayed set; on the timer-driven path, that flag can suppress scheduling future work.

Guarantee scheduler cleanup with `finally`, finish independent deliveries, and report/aggregate errors afterward according to an explicit policy. Catch storage read/write failures and route them through `onError`.

### R15 — P2: Resource failure/cancellation state is inconsistent

**Reproduced.** A synchronously throwing loader leaves both resource implementations in `Pending` without a pending promise. Calling `abort` on a pending single-slot resource likewise leaves `Pending` with no request.

Both loaders are invoked before normalizing synchronous exceptions: [single-slot start](../lib/src/Carburetor/Resource/ResourceCarburetor.ts#L113), [cache fetch](../lib/src/Carburetor/Resource/Cache/ResourceCache.ts#L345). A function typed to return a promise can still throw before returning it.

Normalize loader invocation into the request/error lifecycle. Define cancellation as `Idle`, an explicit cancelled status, or restoration of prior success. The existing single-slot abort test explicitly expects perpetual `Pending`, so this part is a contract/test-oracle change, not an unnoticed mismatch with that test.

### R16 — P2: The JS lint rules miss real cache writes and leak exemptions between classes

**Reproduced through ESLint.**

1. `this.useResource(cache, id); cache.load(id)` inside render produces no `no-store-write-in-render` report.
2. `this.useCarburetor(cache); cache.getEntry(id)` produces an incorrect “changes a store” report.
3. Class A calls `helper` from `preEmit`. Class B has its own unrelated `helper` that writes draft without publishing. B is reported when tested alone, but stops being reported when A is in the same file.

[noStoreWriteInRender](../plugin/src/Rules/Writes/noStoreWriteInRender.mts#L18) omits `useResource` from store discovery and cache read methods from its allowlist. [requireEmitAfterDraftWrite](../plugin/src/Rules/Writes/requireEmitAfterDraftWrite.mts#L85) keys its exemption graph by method name across the entire file, without owning-class identity.

Update the resource API model and scope exemption graphs to their owning classes. Add multiple-class fixtures and positive/negative cache controls. More generally, matching names and finding a call somewhere in a method is not control-flow proof that every write publishes or every lifecycle path calls `super`.

## Additional limitations and performance concerns

These are separate from the release-priority failures above.

- **Object-array no-ops publish.** Reproduced: sorting an already sorted two-element array of objects caused a notification. [createWriteProxy](../lib/src/Carburetor/Store/Tracking/createWriteProxy.ts#L51) compares raw stored values with proxy values and writes the proxies back. Unwrap draft values before assignment/comparison and verify moving objects between paths. The demo's string ID array does not expose this.
- **Snapshot isolation is conditional.** [deepClone](../lib/src/Carburetor/Store/Utils/deepClone.ts#L9) shares Map/Set/Date/class instances, omits symbol-keyed object properties, and has no cycle handling. The non-plain sharing is documented in source and explicitly tested, so it is a known design limitation. Public “detached deep copy” and undo guarantees need the same qualification or a codec/validation contract.
- **Tracking is not allocation-free.** Each `read` creates a new root proxy; nested traversals build proxies, maps, and path strings. Every committed component render replaces its indexed subscription. An unchanged parent boundary helps, but frequent renders still pay this cost.
- **Array writes are intentionally coarse.** Assigning an array index invalidates its array path. Document when a keyed dictionary plus an order array is preferable.
- **Generic path keys are not escaped.** [joinPath](../lib/src/Carburetor/Store/Paths/joinPath.ts#L4) conflates dotted property names with nested paths; cache keys escape dots, arbitrary store keys do not. Empty keys and `*` also need an explicit path contract.
- **Write-proxy caches retain previously visited branches.** [createProxyCache](../lib/src/Carburetor/Store/Tracking/createProxyCache.ts#L14) holds strong references by path and has no delete-time eviction. This is a code-level retention concern for churn under a stable parent object, not a measured heap-growth claim.
- **The demo performs whole-list work on each edit.** [TodoCarburetor.preEmit](../lib/src/ToDo/Carburetors/TodoCarburetor.ts#L49) recounts all items and sorts the order array on every title change. Even an already ordered array must be visited. One rendered row therefore does not mean constant work per keystroke.
- **History and persistence scale with total state.** History copies state on every observed update; lowering the history limit reduces retained memory, not the cost of each snapshot. Persistence and DevTools also process whole snapshots. Consider opt-in selection, coalescing, or patches when real profiling warrants them.
- **Concurrent rendering remains an explicit limitation.** The README already acknowledges no consistency guarantee within a concurrent render pass. Commit-time version correction is useful, but live mutable reads are not render snapshots. Keep this limitation prominent. The interop snapshot defect in R05 additionally contradicts the stronger guarantee claimed for that entry point.
- **Lifecycle semantics need sharper documentation.** Named effects run synchronously in class commit lifecycles, not with passive `useEffect` timing. Effects still require dependency arrays. Specify what happens when a named effect is omitted on a later pass, and how failed setup/cleanup affects other effects and subscriptions.
- **Cache restore needs an explicit lifecycle.** Runtime request/controller metadata is not part of snapshots. Define restoring over active requests and hydrating an entry marked `refreshing`; otherwise serialized status and actual work can disagree. These restore races were identified by inspection and require targeted regressions.
- **Documentation has drift.** `docs/promise-cache.md` lists optional `invalidate(args?)` / `forget(args?)` forms and optional immediate refetch, while the implementation provides separate `invalidateAll` / `forgetAll` and no such refetch option. The introductory “No dependency arrays” promise also conflicts with the effect API.

## Usability recommendations

For a team comfortable with classes, the basic `store action → tracked read → component update` workflow is approachable. The current learning burden comes from the exceptions: tracked and untracked reads, escaping proxies, manual publication, unique effect names, lifecycle ownership, scoped tokens, and compatibility with hook-oriented libraries.

1. Make `update` the normal, safe write path. Keep manual draft/publication APIs clearly advanced, with an explicit contract for errors and untracked writes.
2. Publish a precise data model: JSON-like trees, graphs, accessors, frozen values, symbols, and non-plain objects should each have a stated support level. Enforce unsupported cases in development.
3. Stabilize both component and interop correctness before expanding the API. A reliable bridge is important for incremental adoption in an existing application.
4. Add a small quick start that includes loading, errors, cancellation, cleanup, and scope hydration. Explain how to reuse behavior across class components without inheriting multiple unrelated base classes.
5. Make effect dependencies and timing explicit. If an automatically tracked reaction API is desired, specify its lifecycle first; renaming a hooks-shaped effect does not remove its dependency problem.
6. Offer developer-only explanations of why a component updated: changed paths, recorded reads, and the source of an invalidation. An empty subscription used to render store-derived content should be easy to diagnose.
7. Present the value proposition as selective React updates with explicit store actions. Support broader speed claims with representative application measurements.

## Verification and implementation order

First repair subscription lifecycle and dependency correctness: R01–R07 and R10. Next stabilize resource lifecycle and request behavior: R08–R09, R11–R12, and R15. Then harden mutation/delivery failure paths and the lint rules: R13–R14 and R16. Some of these can share underlying fixes, but each needs its own behavioral regression.

The regression set should include:

- Root StrictMode mounting followed by a store write; unmount cleanup; separately, Suspense hide/reveal.
- Unobserved computed reads, first subscription after intervening writes, chains, diamonds, and transactions affecting multiple stores.
- Selector/source changes at equal versions; stable conditional selectors; equal selected values with changed dependencies; object-valued snapshots.
- Object presence, aliases/accessors or their explicit rejection, descriptor mutations, frozen values, and moving draft objects.
- Successful cache load followed by failed stale refresh; full-cache Suspense; concurrent settlement over capacity; synchronous loader throws; cancellation.
- Hydration between independently initialized processes/bundles, plus request state during restore.
- Throwing mutation bodies, throwing subscribers/storage, scheduler recovery, and multiple-class lint fixtures.

After correctness is established, measure an actual editing or streaming workflow in a production build: interaction-to-paint latency, React commit work, derivation time, subscription churn, allocation/GC, and retained memory. Compare equivalent state shapes, component boundaries, batching, and functionality. The existing matcher microbenchmark is useful for its own subsystem; it cannot establish application-level superiority.

No fixes were made in this review. The intended next engineering step is to repair these mechanisms and add their regression cases, while keeping the compact core API.
